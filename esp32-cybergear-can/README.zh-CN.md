# ESP32-S3 + CyberGear CAN 实验

这个独立 ESP-IDF 示例用于验证以下实体链路：

```text
ESP32-S3-DevKitC-1 N16R8
        │ GPIO4 / GPIO5
        ▼
SN65HVD230 CAN 收发器板
        │ CANH / CANL
        ▼
CyberGear 微电机（独立 24 V 供电）
```

它使用 CyberGear 厂商协议：Classical CAN、1 Mbit/s、29 位扩展帧。ESP32-S3 时序显式使用每 bit 20 个时间量子、80% 采样点，与已正常工作的 STM32 对照实现一致，不再沿用 ESP-IDF 在 ESP32-S3 上的默认时序。它不是 xbot Robot Bus V1 示例，不能与 250 kbit/s Robot Bus 节点直接共用同一条 CAN 总线。

## 安全边界

CyberGear 是可产生明显扭矩的 24 V 执行器。首次测试必须满足：

- 电机卸载、输出端悬空并可靠固定；不要安装在轮椅或载人机构上测试。
- 使用独立、带限流的 24 V 台式电源，并准备可以立即断开 24 V 的开关。
- 接线和测量终端电阻时保持电机电源关闭。
- 24 V 只能进入电机的 `VBAT+`；不得接入 ESP32 或 SN65HVD230 的 3.3 V 引脚。
- 这块 SN65HVD230 板没有隔离，电机电源负极、收发器 GND 与 ESP32 GND 必须共地。
- 默认固件不执行位置移动；只有显式启用 Kconfig 选项后才允许 `+2π rad`（`360°`）往返。Motion 必须清空整个一圈扫过的区域，严禁用手堵转。

软件会在反馈超时、类型 2 状态故障、类型 21 故障/预警帧、温度达到 70 °C，以及 TWAI bus-off/错误告警时中止。每个主动控制阶段还要求反馈处于 Motor 模式，位置、速度和转矩是协议范围内的有限值。实测速度绝对值在零输出阶段必须小于 `0.5 rad/s`，在 Motion 阶段必须小于 `1.0 rad/s`；反馈转矩绝对值在零输出阶段必须小于 `1.0 N·m`、在 Motion 阶段必须小于 `10.0 N·m`；相对当前目标的位置误差绝对值必须小于 `0.10 rad`（约 `5.7°`）。发送命令前和收到反馈后，达到任一阈值均中止。每次发送前，固件还会估算 `前馈 + Kp × (目标位置 - 实测位置) + Kd × (目标速度 - 实测速度)`，其绝对值也必须严格小于该阶段的转矩阈值。Motion 使用当前插值目标。这些都是软件估算或延迟观测，不是硬件限矩、限速或断电机制。

异常退出时，程序会尝试发送停止命令并短暂等待匹配的 Reset 模式反馈，然后再关闭 TWAI。正常的首次和最终停止也要求 Reset 模式，Motor 模式反馈不能确认停止。这些暂定软件检查不是硬件速度或位置限制，不能替代机械固定、限流和实体断电开关。CAN 或 MCU 掉电可能导致停止命令无法送达；关闭 TWAI 不等于切断电机电源。

## 硬件接线

ESP32-S3 到 SN65HVD230：

| ESP32-S3 | SN65HVD230 板 | 原理图连接器 |
|---|---|---|
| GPIO4 | CAN_TX / D | P1 pin 1 |
| GND | GND | P1 pin 2 |
| 3V3 | 3.3V | P1 pin 3 |
| GPIO5 | CAN_RX / R | P1 pin 4 |

收发器、电机和电源：

| SN65HVD230 / 电源 | CyberGear 一体接口 |
|---|---|
| P2 pin 2 CANH | pin 4 CAN_H |
| P2 pin 1 CANL | pin 3 CAN_L |
| ESP32 / 收发器 GND | pin 2 电源负极 |
| 外部 24 V 正极 | pin 1 VBAT+ |

建议使用不超过 1 m 的短线，并将 CANH/CANL 绞合。不要仅凭连接器方向猜测引脚；上电前按板卡原理图和电机手册检查连续性。

## 终端电阻

当前 SN65HVD230 板在 CANH 与 CANL 之间焊接了固定的 `120 Ω` 电阻，且没有关闭跳线，因此它应位于总线端点。

完整接线但断电时，测量 CANH 与 CANL：

- 约 `60 Ω`：总线两端各有一个 120 Ω 终端，可以继续检查。
- 约 `120 Ω`：万用表只能看到一个简单终端；改变总线前应先从电机正式资料确认其终端配置。
- 接近开路、读数不稳定或明显偏离：停止上电并检查接线、终端和测量位置。断电电机内部电子电路可能使读数非线性或随时间变化；不能只根据不稳定的电阻读数计算或增加终端电阻。

## 环境

- ESP-IDF 5.5.x
- ESP32-S3 target
- CMake 和主机 C 编译器（用于协议单元测试）

加载 ESP-IDF：

```bash
. /path/to/esp-idf/export.sh
```

如果 ESP-IDF 安装在其他目录，请改用对应的 `export.sh`。

## 先运行协议和运动逻辑测试

在本仓库根目录运行：

```bash
cmake -S esp32-cybergear-can/test \
  -B esp32-cybergear-can/build-host
cmake --build esp32-cybergear-can/build-host
ctest --test-dir esp32-cybergear-can/build-host --output-on-failure
```

测试会检查：

- 控制帧 bits 23..8 正确承载前馈扭矩，而不是主机 ID；
- 使能和停止帧 ID；
- 位置、速度、扭矩、Kp、Kd 的范围钳制和大端编码；
- 设备 ID、类型 2 状态反馈与类型 21 故障反馈解析；
- 非法长度、错误主机 ID 和非有限浮点输入拒绝；
- 单程 10 秒的整圈轨迹、起终点、协议上限附近反向、非法输入，以及分阶段速度阈值、非法阈值、跟随误差、模式检查和零输出诊断配置；
- Motion 的 `Kp=90.0`、`Kd=1.0`、零前馈转矩，以及严格的 `10.0 N·m` 反馈与合成指令出力边界；
- 从固件实际使用的时序计算并确认 1 Mbit/s 和 80% 采样点。

主机测试和固件构建成功不代表已验证实体电机运动。

## 默认构建：只验证通信和零输出

```bash
cd esp32-cybergear-can
idf.py set-target esp32s3
idf.py build
```

确认 `CONFIG_CYBERGEAR_RUN_MOTION_TEST` 已关闭；复用之前开启过 Motion 的本地 `sdkconfig` 时尤其要检查。烧录和启动按下方的受控步骤执行，把 `PORT` 替换为实际串口，例如 `/dev/cu.usbmodem1101`。

默认流程只执行一次：

1. 以 1 Mbit/s 启动 TWAI。
2. 立即发送停止命令并要求收到 Reset 模式反馈。
3. 请求并验证 CyberGear 设备 ID。
4. 发送使能命令并要求进入 Motor 模式。
5. 以反馈位置为目标，发送 500 ms 的零扭矩、`Kp=0`、`Kd=0` 控制帧。
6. 再次停止，收到 Reset 模式反馈后关闭 TWAI。

任何阶段未收到预期反馈或反馈不安全都会中止，不会继续进入下一阶段。

## 60 秒零输出 CAN 链路压力测试

再次测试运动前先使用这个诊断构建。它保持 Motion 关闭，只把静止零输出阶段延长到 60 秒。目标始终是使能后测得的初始位置，目标速度、前馈扭矩、`Kp` 和 `Kd` 均为零；固件以标称 50 Hz 持续发送控制帧并要求匹配反馈，现有身份、模式、故障、温度、速度、反馈转矩、跟随误差、超时和致命 TWAI 检查全部保留。

使用独立构建目录，不改变项目日常使用的 `sdkconfig`：

```bash
idf.py -B build-link-soak \
  -D SDKCONFIG=build-link-soak/sdkconfig \
  -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.link-soak.defaults' \
  set-target esp32s3
idf.py -B build-link-soak \
  -D SDKCONFIG=build-link-soak/sdkconfig \
  -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.link-soak.defaults' \
  build
```

启动日志必须显示 `link_soak=ENABLED, motion=disabled`。成功要求完整运行 60 秒，最终 TWAI 状态为 `TEC=0`、`REC=0`、`tx_failed=0`、`bus_errors=0`，随后收到 Reset 模式停止确认并关闭 TWAI；任一致命告警都会立即中止。该模式不请求位移或出力，但测试期间电机处于使能状态，不能阻止外力或硬件故障导致的运动，仍须保持空载并准备 24 V 实体断电开关。

## 显式启用 360° 往返测试（单程 10 秒）

只有完成默认测试、确认反馈值和终端正常后，才执行：

```bash
idf.py menuconfig
```

进入 `CyberGear CAN example`，启用：

```text
Explicitly allow the 360-degree out-and-back test (10 seconds per leg)
```

然后重新构建：

```bash
idf.py build
```

烧录和启动按下方的受控步骤执行，不要在电机带电时使用合并的 `flash monitor` 命令。

Motion 流程在零输出结束后重新读取最新实测位置作为起点，只执行一次往返：

1. 在 **10 秒**内，将位置目标从起点线性增加至 `起点 + 2π rad`（`360°`）。
2. 再用 **10 秒**，将位置目标线性减小回同一起点。
3. 发送停止，要求 Reset 模式反馈，然后关闭 TWAI，不循环运行。

如果起点接近协议正上限，程序会改为 `-2π rad`。两段均使用 `Kp=90.0`、`Kd=1.0`，目标速度按轨迹斜率带方向计算（本档为 `±0.628 rad/s`），前馈扭矩保持为零。控制周期标称为 20 ms，每次控制必须在 250 ms 内收到反馈；每段起终点都会发送并检查反馈。调度和反馈延迟可能使实际耗时略长。运动往返约 **20 秒**，另加零输出、启动和停止阶段的时间，不是连续旋转。

标称**目标变化速度**约为 `0.628 rad/s`（`36°/s`，即 6 rpm），目标在 10 秒内变化一圈；Motion 的目标速度项也使用同一带符号数值，使 Kd 围绕预期轨迹速度抑制速度误差，而不是抵消所有运动。它不是电机实际速度的硬上限，零前馈扭矩也不等于总转矩上限。协议量化、摩擦和有限增益仍可能导致跟随滞后或粘滑。阶段结束日志会输出目标位置、实测位置和误差；命令执行完成不代表电机已到达目标。

位置和速度反馈项让这套配置可以随负载变化：没有反向负载且跟随误差很小时，输出转矩很小；负载增大导致位置或速度误差增大时，控制器会自动提高出力以继续跟随同一轨迹。每次发送前，固件会按实测速度的实际方向计算完整控制器出力估算；Motion 阶段一旦其绝对值达到 `10.0 N·m` 就中止，避免各自仍在阈值内的位置误差和速度误差叠加成超过该软件边界的指令。这仍是基于模型的发送前检查，不是电机硬限矩。

Motion 的 1.0 rad/s 异常阈值用于容纳目标变化，零输出阶段保留原来的 0.5 rad/s 阈值；0.10 rad 跟随误差检查保持不变。`Kp=7.5 / Kd=0.3`、`Kp=30.0 / Kd=1.0` 和 `Kp=90.0 / Kd=1.0` 三档均分别观察到一次空载整圈往返完成。`Kp=90.0` 本次去程/回程终点误差为 `+0.0001/+0.0012 rad`；在约 250 ms 间隔的常规 INFO 遥测样本中，速度绝对值最大为 `0.583 rad/s`，反馈转矩绝对值最大为 `1.422 N·m`，反馈温度最大为 `28.6 °C`。用户确认运动和声音正常。这些单次记录仍不能验证变化负载、堵转或可靠性。说明书标明额定负载 `4 N·m`、峰值负载 `12 N·m`；`Kp=500` 和 `12 N·m` 是协议/峰值边界，不是台架推荐指令。Motion 使用严格的 `<10.0 N·m` 反馈与合成指令出力检查，零输出仍为 `<1.0 N·m`，但这些只是软件观测和估算，不是硬件电流/转矩限幅。固件不会写入电机的 `limit_torque`、`limit_cur` 或电流环参数。

这只是低参数、无负载的通信实验，不代表电机控制性能、机械安全性或载人系统可用性已经验证。

此前小角度和 180° 台架日志既有完成的往返，也有 CAN 总线错误导致的中止。一次 180° 测试还因实测跟随误差达到 -0.1004 rad 而停止。最后一次完成的半圈测试，去程和回程终点误差分别为 -0.0065 rad、+0.0061 rad，但这不代表链路可靠性或更快的整圈测试已验证。改变角度或时间没有解决这些故障，固件仍会在错误发生时中止，测试可能提前停止。不要关闭保护或反复复位强行跑完；应先切断 24 V，检查日志和实体总线。

固件启动会记录 `reset reason=<数字> (<名称>)`，用于区分外部复位、USB、棕断、看门狗和软件异常；控制阶段仍以 50 Hz 检查反馈，但常规 INFO 遥测约每 250 ms 输出一次，便于保存完整日志。

## 受控烧录和启动

1. **断开电机 24 V**，保留 ESP32 的 USB 连接，关闭已有串口监视器。确认电机卸载并固定、接线和终端正确，实体断电开关在手边。测量终端电阻时还需断开 USB 电源。
2. 手动进入 ROM 下载模式：按住 **BOOT**，点按并松开 **RESET**，再松开 **BOOT**。确认当前串口名，USB 重新枚举可能改变名称。
3. 加载 ESP-IDF 环境并构建所需配置后，执行不自动复位启动的烧录命令：

   ```bash
   cd build
   python -m esptool --chip esp32s3 --port PORT \
     --before no_reset --after no_reset write_flash @flash_args
   cd ..
   ```

   烧录全程保持 24 V 关闭，此时不要点按 RESET。若使用其他构建目录，须使用该目录的 `flash_args` 和对应固件。
4. 启动与固件对应的串口监视器，不主动复位开发板：

   ```bash
   idf.py -p PORT monitor --no-reset --timestamps
   ```

   先按 **Ctrl+T**，再按 **Ctrl+L** 开启文件日志，监视器会显示日志路径。打开或重新连接 USB 串口时保持电机 24 V 关闭，因为 USB/驱动行为仍可能影响开发板。保持监视器打开。
5. 确认输出端周围无人触碰、断电开关就绪后，接通限流的 24 V 电源，再有意识地点按 **RESET 一次**。核对启动日志的 `link_soak` 和 `motion` 状态是否符合预期，观察反馈。若监视器断开，先切断 24 V 再重新打开。
6. 收到最终 Reset 模式反馈并关闭 TWAI 后，**断开 24 V**。如果出现异常运动或测试中止，立即切断 24 V，不要只依赖软件停止。

Motion 固件在**每次启动**时都可能执行这套流程，包括复位或 USB 重连；它没有额外的串口解锁命令。运动测试结束后，应关闭 Motion 配置并重新构建、烧录。

## 成功判据

串口日志应显示：

- `device found`，且电机 ID 与配置一致；
- 停止后收到 Reset 模式的类型 2 反馈，主动控制阶段持续处于 Motor 模式；
- 位置、速度、扭矩和温度数值合理；
- 默认构建显示 Motion 为 `disabled`；
- 最后显示测试完成、收到停止反馈并关闭 TWAI。

开启 Motion 时，还必须检查去程和回程的终点误差，以及实际两个方向的整圈运动；仅命令执行完成不能作为实体运动验收。

以下任一情况都视为失败并应切断 24 V：

- `device ID response timeout` 或 `control feedback timeout`；
- 反馈模式不符，或实测速度、反馈转矩、跟随误差、合成指令出力检查拒绝；
- `fatal TWAI alert`、bus-off、发送失败或接收帧格式错误；
- 非零电机故障位或类型 21 故障/预警帧；
- 异常退出后停止命令未获得确认；
- 温度达到 70 °C；
- 电机运动方向、噪声、振动或电流明显异常。

## 配置项

`idf.py menuconfig` 的 `CyberGear CAN example` 菜单提供：

- 电机 ID，默认 `127 / 0x7F`；
- 主机 ID，默认 `253 / 0xFD`；
- TWAI TX GPIO，默认 GPIO4；
- TWAI RX GPIO，默认 GPIO5；
- 60 秒零输出 CAN 链路压力测试开关，默认关闭；
- 360° 往返 Motion 显式开关（单程 10 秒），默认关闭。

板卡原理图和器件数据手册见 [xbot 硬件资料](https://github.com/miclle/xbot/tree/main/hardware/SN65HVD230-CAN-Board)。
